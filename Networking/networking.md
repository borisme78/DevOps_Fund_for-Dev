# Мережі для full-stack розробника: детальний розбір



## 1. Клієнт-серверна модель

**Суть:** дві ролі. Клієнт просить, сервер відповідає.

| | Клієнт | Сервер |
|---|---|---|
| Ініціює розмову? | Так | **Ніколи** |
| Що робить | Надсилає запит, чекає відповідь | Слухає порт, обробляє запити |
| Кількість | Багато | Один обслуговує багатьох |
| Приклад | Браузер, React-застосунок, Postman | Node.js, Nginx, PostgreSQL |

**Важливо:** «клієнт» і «сервер» це **ролі програм**, а не типи комп'ютерів. Ваш Node.js бекенд для БД є клієнтом, а для браузера сервером. Одна машина може виконувати обидві ролі.

```
Браузер ──запит──▶ Бекенд ──запит──▶ База даних
        ◀─відповідь─       ◀─відповідь─
(клієнт)         (сервер і клієнт)    (сервер)
```

**Чому це важливо:** сервер повинен **слухати** певний порт, тому ви запускаєте `app.listen(3000)`. Клієнт порту наперед не знає, ОС дає йому випадковий.

## 2. Моделі TCP/IP, OSI та інкапсуляція

### Навіщо рівні?
Кожен рівень вирішує свою задачу й не знає про деталі інших. HTTP не цікавить, чи дані йдуть по Wi-Fi чи по кабелю.

### TCP/IP (4 рівні), яку використовує інтернет

| Рівень | Задача | Приклади | Одиниця даних |
|---|---|---|---|
| **Application** | Протоколи, з якими працює застосунок | HTTP, DNS, SSH | Data |
| **Transport** | Доставка між застосунками (порти) | TCP, UDP | Segment / Datagram |
| **Internet** | Адресація й маршрутизація між мережами | IP, ICMP | **Packet** |
| **Network Access** | Передача в межах одного з'єднання | Ethernet, Wi-Fi | **Frame** |

### OSI (7 рівнів), теоретична модель

Зверху вниз: **Application → Presentation → Session → Transport → Network → Data Link → Physical**

Відповідність: рівні 5-6-7 OSI = Application в TCP/IP. Рівні 1-2 OSI = Network Access в TCP/IP.

**Мнемоніка знизу вгору:** *Please Do Not Throw Sausage Pizza Away*.

### Інкапсуляція: найважливіша ідея

Уявіть лист у кількох конвертах. Кожен рівень додає свій «конверт» (заголовок):

```
Application:     [  Дані: GET /users  ]
Transport:    [TCP][  Дані  ]                        ← segment (+ порти)
Internet:  [IP][TCP][  Дані  ]                       ← packet (+ IP-адреси)
Network:[Eth][IP][TCP][  Дані  ][Trailer]            ← frame (+ MAC-адреси)
Physical:  010110011101010...                        ← біти
```

Отримувач розпаковує у зворотному порядку: **декапсуляція**.

**Що кожен заголовок додає:**
- TCP/UDP заголовок: **порти** відправника й отримувача
- IP заголовок: **IP-адреси** відправника й отримувача
- Ethernet заголовок: **MAC-адреси**

### Назви одиниць даних

| Рівень | Назва |
|---|---|
| Transport | **Segment** (TCP) / Datagram (UDP) |
| Network | **Packet** |
| Data Link | **Frame** |
| Physical | **Bits** |

## 3. Порти

**Порт** це число від 0 до 65535 (16 біт), яке вказує, **який застосунок** на машині має отримати дані.

**Проблема, яку він вирішує:** у вас один мережевий кабель, але одночасно працюють браузер, Teams, Spotify, Git. Як ОС розуміє, кому віддати вхідний пакет? За **портом**.

### Три діапазони

| Діапазон | Назва | Для чого |
|---|---|---|
| 0 - 1023 | Well-known | Стандартні служби (потрібні права root/admin) |
| 1024 - 49151 | Registered | Зареєстровані застосунки (3000, 5432, 8080) |
| 49152 - 65535 | Dynamic / Private | Тимчасові порти клієнтів |

### Як це працює на практиці

Коли ви відкриваєте `https://example.com`:

```
Ваш браузер (клієнт)               Сервер
IP: 192.168.1.5                    IP: 93.184.216.34
Source port: 52341 (випадковий)  ──▶  Destination port: 443 (well-known)
```

Клієнт отримує **випадковий динамічний порт**, сервер слухає **відомий порт**. У відповіді вони міняються місцями.

### Таблиця для запам'ятовування

| Порт | Протокол | Примітка |
|---|---|---|
| **22** | SSH | безпечне віддалене керування |
| **53** | DNS | перетворення імен на IP |
| **80** | HTTP | веб без шифрування |
| **443** | HTTPS | S = Secure, число більше |
| 21 | FTP (команди) | 20 для даних |
| 23 | Telnet | незахищений, замінений SSH |
| 25 | SMTP | відправка пошти |
| 110 | POP3 | отримання пошти |

### Сокет
**Сокет = IP-адреса + порт**, наприклад `93.184.216.34:443`. З'єднання однозначно визначається парою сокетів (клієнт і сервер).

### Помилка, яку ви зустрінете
`EADDRINUSE: address already in use :::3000` означає, що порт 3000 вже зайнятий іншим процесом. Рішення: зупинити той процес або обрати інший порт.

## 4. Різниця між MAC, IP і портом

Найкраща аналогія: **доставка посилки в багатоквартирний будинок**.

| | MAC | IP | Port |
|---|---|---|---|
| **Аналогія** | Особисті дані людини (паспорт) | Адреса будинку | Номер квартири |
| **Що ідентифікує** | Мережеву карту (пристрій) | Місце в мережі | Застосунок |
| **Рівень** | 2 (Data Link) | 3 (Network) | 4 (Transport) |
| **Тип** | Фізична | Логічна | Програмна |
| **Розмір** | 48 біт | 32 біти (IPv4) / 128 (IPv6) | 16 біт |
| **Приклад** | `1A:2B:3C:4D:5E:6F` | `192.168.25.100` | `443` |
| **Змінюється?** | Зазвичай ні (зашита в карту) | Так, залежно від мережі | Залежить від програми |

### Чому потрібні і MAC, і IP?
- **IP** працює «глобально»: за ним роутери знаходять шлях через інтернет.
- **MAC** працює «локально»: у межах одного сегмента (вашого Wi-Fi) пристрої знаходять один одного.

Коли пакет іде через кілька роутерів, **IP-адреси залишаються тими самими** (відправник і кінцевий отримувач), а **MAC-адреси змінюються на кожному «стрибку»**.

### Формат MAC-адреси
- 6 груп по 2 шістнадцяткові символи (0-9, A-F)
- Перші 3 групи (OUI) визначають виробника
- `FF:FF:FF:FF:FF:FF` це broadcast (для всіх)

## 5. DNS: як ім'я стає IP

**Проблема:** люди пам'ятають `google.com`, а комп'ютери працюють з IP. **DNS** це «телефонна книга інтернету».

### Структура доменного імені (читається справа наліво)

```
   www  .  softserve  .  com  .
    │         │          │     └─ Кореневий домен (Root)
    │         │          └─────── TLD (домен верхнього рівня)
    │         └────────────────── Домен другого рівня
    └──────────────────────────── Піддомен
```

### Як відбувається пошук (ієрархічно)

```
1. Ви: "Який IP у softserve.com?"
       ▼
2. Рекурсивний DNS (зазвичай провайдера або 8.8.8.8)
       ├─▶ Root-сервер:   "Спитай сервер .com"
       ├─▶ TLD-сервер .com: "Спитай сервер softserve.com"
       └─▶ Авторитетний сервер softserve.com: "IP = 23.229.148.197"
       ▼
3. Відповідь повертається вам (і кешується)
```

### Кешування
Щоб не робити цей довгий шлях щоразу, відповіді кешуються: у браузері, в ОС, у DNS-резолвері. Тому після зміни DNS-запису «зміни доходять не одразу» (це залежить від **TTL**).

### Типові DNS-записи (корисно для деплою)

| Запис | Що робить |
|---|---|
| **A** | домен → IPv4 |
| **AAAA** | домен → IPv6 |
| **CNAME** | домен → інший домен (аліас) |
| **MX** | куди доставляти пошту |

### Практика
```bash
nslookup google.com
dig google.com
```

## 6. Приватні IP-діапазони, localhost, 0.0.0.0

### Навіщо приватні адреси?
IPv4-адрес лише ~4,3 млрд, на всі пристрої не вистачає. Тому створили діапазони, які **не маршрутизуються в інтернеті** й можуть повторюватися в різних локальних мережах.

### Три приватні діапазони (RFC 1918)

| Діапазон | Префікс | Адрес | Де зустрінете |
|---|---|---|---|
| `10.0.0.0` - `10.255.255.255` | /8 | ~16,7 млн | Корпоративні мережі, AWS VPC |
| `172.16.0.0` - `172.31.255.255` | /12 | ~1 млн | **Docker** (172.17.x.x) |
| `192.168.0.0` - `192.168.255.255` | /16 | 65 536 | Домашні роутери |

**Підступ:** діапазон `172.16.0.0/12` закінчується на `172.31.x.x`, а не `172.255.x.x`. Адреса `172.32.0.1` уже **публічна**.

### Спеціальні адреси

| Адреса | Значення | Практичне застосування |
|---|---|---|
| **127.0.0.1** | Loopback (localhost): «я сам». Весь блок `127.0.0.0/8` зарезервований | Запуск і тестування локально |
| **0.0.0.0** | «Усі інтерфейси» (на сервері) або «невизначена адреса» | Налаштування прослуховування |
| **169.254.x.x** | Link-local: ОС сама призначила адресу, бо DHCP не відповів | Ознака проблеми з мережею |
| **255.255.255.255** | Broadcast | Для всіх у мережі |

### Різниця між 127.0.0.1 і 0.0.0.0 (дуже практичне питання)

```js
app.listen(3000, '127.0.0.1');  // тільки з цього комп'ютера
app.listen(3000, '0.0.0.0');    // з будь-якого мережевого інтерфейсу
```

**Класична проблема Docker:** застосунок у контейнері слухає `127.0.0.1`, і ззовні до нього не достукатися. Рішення: слухати `0.0.0.0`.

## 7. ping і traceroute

### ping: «ти там?»
Перевіряє, чи доступний вузол, і вимірює затримку.

```bash
ping google.com
```

**Як працює:** відправляє **ICMP Echo Request**, чекає **ICMP Echo Reply**.

**Приклад виводу:**
```
64 bytes from 142.250.74.14: icmp_seq=1 ttl=117 time=24.3 ms
```
- `time` це затримка (round-trip time)
- `ttl` це залишок «часу життя» пакета

**Що показує результат:**
- Відповідь є: вузол доступний, мережа працює
- «Request timed out» / «Destination unreachable»: вузол недоступний, або заблокований firewall (багато серверів ігнорують ping навмисно)
- Працює `ping 8.8.8.8`, а `ping google.com` ні: проблема з **DNS**

### traceroute: «яким шляхом?»
Показує всі роутери на шляху до цілі.

```bash
traceroute google.com     # Linux/Mac
tracert google.com        # Windows
```

**Як працює:**
1. Відправляє пакет з **TTL = 1**. Перший роутер зменшує TTL до 0, відкидає пакет і відповідає **ICMP Time Exceeded**. Так ми дізнаємося про перший роутер.
2. Відправляє з **TTL = 2**. Те саме, але відповідає другий роутер.
3. Так далі, поки пакет не дійде до цілі.

**Для чого:** знайти, **на якому саме «стрибку»** виникає затримка або обрив.



## 8. Маски й префікси

### Ідея
IP-адреса складається з двох частин: **мережа** (старші біти) і **хост** (молодші біти). Префікс показує, скільки бітів належить мережі.

```
192.168.25.100/24
└──────┬──────┘ └┬┘
    адреса    24 біти під мережу, решта 8 під хости
```

### Маска
Маска це те саме, але у вигляді адреси: одиниці це мережа, нулі це хост.

| Префікс | Маска | Бітів хоста (N) |
|---|---|---|
| /8 | 255.0.0.0 | 24 |
| /16 | 255.255.0.0 | 16 |
| /24 | 255.255.255.0 | 8 |
| /25 | 255.255.255.128 | 7 |
| /30 | 255.255.255.252 | 2 |

### Головна формула
**Кількість хостів = 2ᴺ − 2**, де **N = 32 − префікс**

Мінус 2, бо в кожній підмережі дві адреси зарезервовані:
- **перша** (всі біти хоста = 0): адреса мережі
- **остання** (всі біти хоста = 1): broadcast

### Приклад /24: `192.168.25.0/24`
- N = 32 − 24 = 8
- Хостів: 2⁸ − 2 = **254**
- Мережа: `192.168.25.0`
- Хости: `192.168.25.1` - `192.168.25.254`
- Broadcast: `192.168.25.255`

### Приклад /25: `192.168.25.0/25`
- N = 32 − 25 = 7
- Хостів: 2⁷ − 2 = **126**
- Мережа: `192.168.25.0`
- Хости: `192.168.25.1` - `192.168.25.126`
- Broadcast: `192.168.25.127`

Тобто /25 «розрізає» /24 навпіл: друга половина це `192.168.25.128/25`.

### Як знайти адресу мережі: побітове AND

```
IP:     192.168.25.100  = 11000000.10101000.00011001.01100100
Маска:  255.255.255.0   = 11111111.11111111.11111111.00000000
                          ─────────────────────────────────── AND
Мережа: 192.168.25.0    = 11000000.10101000.00011001.00000000
```

### Де це потрібно вам
- **AWS VPC:** створюєте мережу `10.0.0.0/16` і ділите на підмережі `10.0.1.0/24`
- **Docker networks:** `172.17.0.0/16`
- **Kubernetes:** діапазони для pod-ів і сервісів
- **Конфлікти:** якщо діапазон VPN перетинається з домашнім, виникають баги

### Таблиця для швидкого запам'ятовування

| Префікс | Хостів |
|---|---|
| /30 | 2 |
| /29 | 6 |
| /28 | 14 |
| /27 | 30 |
| /26 | 62 |
| /25 | 126 |
| /24 | 254 |
| /16 | 65 534 |

Закономірність: кожен менший префікс це приблизно вдвічі більше хостів.

## 9. NAT

### Проблема
У вас вдома кілька пристроїв з адресами `192.168.1.x`. Ці адреси приватні й **в інтернеті не маршрутизуються**. Як тоді телефон відкриває сайти?

### Рішення
Роутер має **одну публічну IP** (від провайдера) і підміняє адреси «на льоту».

```
Телефон 192.168.1.10:51000 ──▶ [РОУТЕР з NAT] ──▶ Сайт
                               підміняє на
                               101.89.101.12:40001
```

1. Телефон шле запит з приватною адресою.
2. Роутер замінює адресу відправника на **свою публічну IP** і запам'ятовує відповідність у таблиці.
3. Сайт відповідає на публічну IP роутера.
4. Роутер дивиться в таблицю й передає відповідь потрібному пристрою.

### Типи

| Тип | Що підміняє | Використання |
|---|---|---|
| **SNAT** | Адресу **відправника** | Вихід у інтернет |
| **DNAT** | Адресу **отримувача** | Port forwarding (відкрити сервіс ззовні) |
| **PAT** | IP **і порти** (багато пристроїв → 1 IP) | Домашні роутери (найпоширеніший) |

### Висновок
Ось чому **ваш `192.168.x.x` не видно з інтернету**: він існує лише всередині локальної мережі. Щоб відкрити локальний сервер зовні, потрібен **port forwarding** (DNAT) або тунель (ngrok тощо).

## 10. VPN, DMZ, VLAN

### VPN (Virtual Private Network)
**Зашифрований «тунель»** через публічну мережу, ніби ви підключені напряму до приватної.

| Тип | Сценарій |
|---|---|
| **Remote Access VPN** | Ви вдома підключаєтеся до корпоративної мережі |
| **Intranet VPN** (site-to-site) | З'єднує мережі філій компанії |
| **Client/Server VPN** | Захист зв'язку між двома конкретними вузлами |

**Де зустрінете:** доступ до внутрішніх серверів/БД компанії, до приватних репозиторіїв.

### DMZ (Demilitarized Zone)
Окрема зона для серверів, доступних з інтернету (веб, пошта, DNS).

```
Інтернет ──▶ [Firewall] ──▶ DMZ (веб-сервер)
                │
                └──▶ [Firewall] ──▶ Внутрішня мережа (БД, офіс)
```

**Ідея:** якщо зламають публічний веб-сервер, зловмисник потрапляє лише в DMZ, а не у внутрішню мережу. Приблизний аналог у хмарі: публічні та приватні підмережі в AWS.

### VLAN (Virtual LAN)
Логічно ділить **один фізичний комутатор** на кілька ізольованих мереж.

- Стандарт **IEEE 802.1Q**, працює через **тег** у кадрі (+4 байти) з ID і пріоритетом
- Пристрої з різних VLAN **не бачать один одного** без роутера

**Навіщо:** безпека (гостьовий Wi-Fi окремо від бухгалтерії), менше broadcast-трафіку, гнучкість без перекладання кабелів.
