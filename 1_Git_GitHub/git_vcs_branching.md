# Частина 1. Основи VCS і Git

## 1. Що таке VCS і навіщо він потрібен

**VCS** (Version Control System, система контролю версій) керує змінами в документах, програмах, сайтах та інших наборах файлів.

**Проблеми без VCS:** `project_final.zip`, `project_final_v2.zip`, `project_final_REAL.zip`; не можна відкотитися; не зрозуміло, хто що змінив; два розробники перезаписують роботу одне одного.

### Фундаментальні концепції

| Концепція | Суть |
|---|---|
| Tracking changes | відстеження змін |
| Committing | фіксація змін як нової версії |
| Revisions / change sets | версії та набори змін |
| Getting updates | отримання змін від інших |
| Conflicts | суперечливі зміни одного місця |
| Diffing | перегляд відмінностей |
| Branching and merging | гілки та їх злиття |

### Терміни
- **Repository** (репозиторій): сховище проєкту з усією історією
- **Working copy** (робоча копія): файли, з якими ви працюєте на диску
- **Revision / commit**: окрема збережена версія
- **Merging**: об'єднання змін із різних гілок

### Типи VCS

| | Централізовані | Розподілені |
|---|---|---|
| Сховище | один центральний сервер | у **кожного** повна копія з історією |
| Без мережі | обмежена робота | майже все працює локально |
| Приклади | CVS, Perforce, SVN, TFS | **Git**, Mercurial |

## 2. Що таке Git

**Git** це розподілена система контролю версій з акцентом на швидкість, цілісність даних і нелінійні (з гілками) процеси. Створена **Лінусом Торвальдсом** у 2005 році для розробки ядра Linux. Сьогодні найпоширеніша VCS.

### Що вміє Git
- Переходити між версіями, дивитися різницю, історію окремого файлу
- Ставити **теги** на версії
- Обмінюватися наборами змін між репозиторіями
- Переглядати зміни інших людей

> **Git ≠ GitHub.** Git це програма, GitHub (як і GitLab, Bitbucket) це хмарний сервіс для зберігання репозиторіїв і співпраці.

### Встановлення
```bash
sudo apt install git        # Debian, Ubuntu, Mint
sudo yum install git        # RHEL, CentOS, Fedora
# Windows: https://git-scm.com/download/win
```

### Довідка
```bash
git help <command>
git <command> --help
man git-<command>
```


## 4. Створення репозиторію

| Команда | Що робить |
|---|---|
| `git init` | створити порожній локальний репозиторій |
| `git clone <URL>` | створити локальну копію віддаленого репозиторію |
| `git remote add <name> <url>` | додати віддалений репозиторій |
| `git remote -v` | показати віддалені репозиторії |

```bash

git remote add origin https://github.com/user/project.git
```

`origin` це стандартне ім'я головного віддаленого репозиторію.

## 5. Три стани файлів і три області

### Ключова ідея
Git зберігає **знімки (snapshots)** файлової системи, а не різниці. Майже кожна операція **локальна**.

### Три стани файлу

| Стан | Значення |
|---|---|
| **Modified** | файл змінено, але ще не додано до наступного коміту |
| **Staged** | змінений файл позначено для включення в наступний коміт |
| **Committed** | дані безпечно збережені в локальній базі |

### Три області

```
Working directory  ──git add──▶  Staging area (index)  ──git commit──▶  Git directory (.git)
 (робоча папка)                   (що піде в коміт)                      (локальний репозиторій)
        ▲                                                                       │
        └────────────────────────── git checkout ◀──────────────────────────────┘
```

- **Working directory:** одна версія проєкту, витягнута з бази для роботи
- **Staging area (index):** файл, що зберігає інформацію про те, що піде в наступний коміт
- **Git directory** (`.git`): метадані й база об'єктів проєкту. Саме це копіюється при `git clone`

### Базовий цикл роботи
```bash
git status                  # що змінилось
git add readme.txt          # додати файл у staging
git add .                   # додати все
git commit -m "Add readme"  # зафіксувати
git push origin main        # відправити на сервер
```

## 6. Основні команди

| Команда | Опис |
|---|---|
| `git init` | ініціалізувати репозиторій |
| `git clone` | клонувати репозиторій |
| `git add` | додати файли в staging |
| `git status` | стан поточної гілки |
| `git commit` | зафіксувати staged-файли |
| `git branch [name]` | створити гілку |
| `git checkout [branch]` | переключитися на гілку |
| `git merge [branch]` | злити гілку в поточну |
| `git diff` | різниця незастейджених змін |
| `git log` | історія поточної гілки |
| `git push` | відправити зміни на віддалений репозиторій |
| `git pull` | отримати й злити зміни з сервера (`fetch` + `merge`) |

### Порівняння змін
```bash
git diff                    # робоча папка vs index
git diff --staged           # index vs останній коміт (те саме --cached)
```

### Коміт
`git commit` без `-m` відкриває редактор для повідомлення. З `-m "текст"` повідомлення задається одразу.

## 7. .gitignore

Файл зі списком шаблонів файлів, які Git має ігнорувати (залежності, збірки, секрети, логи).

| Правило | Значення |
|---|---|
| `# коментар`, порожні рядки | ігноруються |
| `*.[oa]` | усі файли `.o` і `.a` |
| `/target/` | каталог `target/` у корені (слеш в кінці означає каталог) |
| `/.classpath` | лише файл у корені |
| `doc/*.txt` | `.txt` безпосередньо в `doc/`, але не `doc/info/arch.txt` |
| `doc/**/*.txt` | усі `.txt` будь-де всередині `doc/` |
| `!lib.a` | **виняток**: не ігнорувати цей файл |

Приклад для Node.js:
```gitignore
node_modules/
.env
dist/
*.log
```

> `.gitignore` діє лише на файли, які Git ще **не відстежує**. Якщо файл уже закомічений, його треба прибрати з індексу: `git rm --cached <file>`.

## 8. Видалення, переміщення, історія

### Видалення та переміщення
```bash
git rm readme.txt            # видалити файл (і з диска, і з git)
git rm --cached readme.txt   # прибрати з git, залишити на диску
git rm -rf src               # видалити каталог
git mv from to               # перейменувати / перемістити
```

### Логи
```bash
git log                      # вся історія
git log -3                   # останні 3 коміти
git log -p -2                # + різниця для останніх 2
git log --since=2.weeks      # за останні два тижні
git log --oneline --graph    # компактно, з графом гілок
git reflog                   # журнал усіх переміщень HEAD (рятує після помилок)
```

## 9. Скасування змін

### Три режими `git reset`

| Команда | Робоча папка | Index | Локальний репозиторій |
|---|---|---|---|
| `git reset --soft <commit>` | не змінюється | не змінюється | **оновлюється** |
| `git reset <commit>` (`--mixed`) | не змінюється | **оновлюється** | **оновлюється** |
| `git reset --hard <commit>` | **оновлюється** | **оновлюється** | **оновлюється** |

- `--soft`: «розкомітити», зміни лишаються в staging
- `--mixed` (за замовчуванням): «розкомітити й розстейджити», зміни лишаються у файлах
- `--hard`: **повністю відкинути**, зміни у файлах **втрачаються безповоротно**

### Інші способи
```bash
git revert <commit-sha>      # створити НОВИЙ коміт, що скасовує вказаний (безпечно для спільних гілок)
git checkout <commit>        # переглянути стару версію (detached HEAD)
git push origin main -f      # примусове оновлення сервера (небезпечно!)
```

| | `reset` | `revert` |
|---|---|---|
| Історія | **переписує** | **додає** новий коміт |
| Для спільних гілок | небезпечно | безпечно |

> **Правило:** не переписуйте історію (`reset --hard` + `push -f`, `rebase`), яку вже забрали інші. Якщо потрібно, краще `--force-with-lease`, який не затре чужі коміти.

## 10. Підключення до GitHub через SSH


## 11. Гілки (branches)

**Гілка** це незалежна лінія розробки. Дозволяє працювати над функцією чи виправленням, не зачіпаючи основний код.

### Команди

| Команда | Що робить |
|---|---|
| `git branch` | список локальних гілок |
| `git branch <name>` | створити гілку |
| `git branch -d <name>` | видалити гілку (після злиття) |
| `git branch -m <name>` | перейменувати поточну гілку |
| `git checkout <name>` | перейти на гілку |
| `git checkout -b <name>` | створити й одразу перейти |
| `git push origin :<name>` | видалити гілку на сервері (сучасно: `git push origin --delete <name>`) |

> У сучасному Git для переходу між гілками також є `git switch <name>` та `git switch -c <name>`.

### Іменування гілок
Префікс показує призначення:
```
feature/feature-name
bugfix/description
hotfix/description
```

## 12. Злиття (merge)

### Робочий цикл: додати функцію в main
```bash
git checkout main
git pull origin main          # оновити main
git checkout -b new-branch    # нова гілка
# ...пишемо код...
git add .
git commit -m "Some commit message"
git checkout main
git merge new-branch          # злити в main
git push origin main
```

### Два види злиття
- **Fast-forward:** якщо main не змінювався, вказівник просто «пересувається» вперед, нового коміту немає.
- **Merge commit** (3-way merge): якщо обидві гілки мали нові коміти, створюється **новий коміт злиття** з двома батьками. `--no-ff` примушує створювати його завжди.

## 13. Конфлікти

Конфлікт виникає, коли в обох гілках змінено **те саме місце** файлу. Git зупиняється й позначає файл:

```
<<<<<<< HEAD
<div id="footer">contact : email.support@github.com</div>
=======
<div id="footer">please contact us at support@github.com</div>
>>>>>>> iss53
```

- між `<<<<<<<` і `=======`: **ваша** версія (поточна гілка, HEAD)
- між `=======` і `>>>>>>>`: версія **з гілки, яку зливаєте**

### Як вирішити
1. Відкрити файл, залишити потрібний варіант (або поєднати), **видалити маркери** `<<<<<<<`, `=======`, `>>>>>>>`.
2. `git add <файл>` для кожного вирішеного файлу.
3. `git commit` (для merge) або `git rebase --continue` (для rebase).

### Корисні команди

| Команда | Призначення |
|---|---|
| `git status` | які файли в конфлікті |
| `git log --merge` | коміти, що спричинили конфлікт |
| `git diff` | відмінності між станами |
| `git checkout -- <file>` | відкинути зміни у файлі (сучасно: `git restore <file>`) |
| `git merge --abort` | **вийти зі злиття** і повернутися до стану до нього |
| `git reset --mixed` | скасувати зміни в робочій папці та index |
| `git reset --hard` | скинути все до останнього коміту (**втрата незакомічених змін**) |

## 14. Rebase

**Rebase** переносить коміти вашої гілки так, ніби вони створені поверх **останньої версії** іншої гілки. Історія стає лінійною, без зайвих merge-комітів.

### Merge vs Rebase

| | **Merge** | **Rebase** |
|---|---|---|
| Історія | зберігається як є, з комітом злиття | **переписується**, лінійна |
| Коміти | старі | **нові** (інші хеші) |
| Безпечність | безпечний для спільних гілок | небезпечний для вже опублікованих гілок |
| Результат | «розгалужений» граф | «пряма лінія» |

```
Merge:                        Rebase:
main:    A──B──C──────M       main:    A──B──C
          \          /                          \
feature:   D──E──F──            feature:         D'──E'──F'
```

### Покроково
```bash
git checkout login-page
git pull
git stash                     # сховати незакомічені зміни
git checkout main
git pull                      # оновити main
git checkout login-page
git rebase main               # перенести свої коміти поверх main
```

При конфліктах під час rebase:
```bash
# виправити файл, потім:
git add ./path/of/file/with/conflicts
git status
git rebase --continue         # продовжити
git rebase --skip             # пропустити поточний коміт
git rebase --abort            # скасувати весь rebase
```

Після rebase історія гілки змінилась, тому для відправки потрібен force push:
```bash
git push --force-with-lease   # безпечніша версія force: не затре чужі зміни
git stash pop                 # повернути сховані зміни
```

> **Золоте правило rebase:** ніколи не робіть rebase гілок (наприклад `main`), якими користуються інші. Rebase доречний лише для **ваших особистих** гілок.

## 15. Зміна історії

### Amend: змінити останній коміт
```bash
git commit --amend -m "updated commit message"   # змінити повідомлення

# забули додати файл у коміт:
git add file2
git commit --amend --no-edit                     # додати до останнього коміту без зміни повідомлення
```

### Squash: об'єднати кілька комітів в один
Інтерактивний rebase:
```bash
git rebase -i HEAD~3          # відкрити останні 3 коміти
```
У редакторі змінити `pick` на `squash` (або `s`) для комітів, які треба «влити» у попередній:
```
pick   ac7dd5f Commit D
squash 5de0b6f Commit C
s      54a204d Commit B
```
Результат: один коміт із трьох. Корисно, щоб перед PR прибрати службові коміти типу «fix typo».

Інші команди в інтерактивному rebase: `reword` (змінити повідомлення), `edit`, `drop` (видалити коміт).

> `amend` і `squash` переписують історію, тому застосовуйте лише до комітів, які ще **не запушені** (або в особистій гілці з `--force-with-lease`).

## 16. Cherry-pick

Бере **окремі коміти** з однієї гілки й застосовує їх в іншу (створюючи нові коміти з тими самими змінами).

```bash
git cherry-pick <commit-id>
git cherry-pick <commit-id-1> <commit-id-2>
git cherry-pick <commitA>..<commitB>       # діапазон (A не включається)
```

**Merge vs Cherry-pick:** merge приносить **всі** коміти гілки, cherry-pick лише **вибрані**.

**Типовий сценарій:** критичний баг виправили в `develop`, і це виправлення терміново потрібне в `main` (hotfix) без решти незавершених змін.

## 17. Стратегії роботи з гілками

### Огляд

| Стратегія | Суть |
|---|---|
| **GitFlow** | багато гілок: `main`, `develop`, `feature`, `release`, `hotfix` |
| **GitHub Flow** | `main` + короткі feature-гілки |
| **GitLab Flow** | `main` + гілки середовищ (pre-production, production) |
| **Trunk-based** | усі інтегруються в одну гілку (trunk) щодня |

### GitFlow
- **main:** стабільний код, що працює в продакшні (кожен реліз має тег)
- **develop:** інтеграційна гілка для наступного релізу
- **feature/\*:** нові функції, відгалужуються від `develop`, зливаються назад у `develop`
- **release/\*:** підготовка релізу, відгалужується від `develop`, **зливається і в `main`, і в `develop`**; тут лише виправлення багів
- **hotfix/\*:** термінові виправлення продакшну, відгалужуються від `main`, зливаються і в `main`, і в `develop`

**Підходить:** великі команди, версійні продукти з довгою підтримкою релізів. **Мінус:** складність.

### GitHub Flow
1. Створити гілку від `main`
2. Робити коміти
3. Відкрити Pull Request
4. Review, оновити гілку з `main` для вирішення конфліктів
5. Злити в `main` і задеплоїти

**Підходить:** малі команди, веб-застосунки, **одна** версія в продакшні. **Плюс:** простота.

### GitLab Flow
Поєднує feature-гілки з відстеженням задач (issues). Працює з `main` одразу (без `develop`). Додає гілки **середовищ**: `main` → `pre-production` → `production`.

**Підходить:** коли є кілька середовищ і окремий staging, відокремлений від production.

### Trunk-based development
- Мінімум довгих гілок: розробники інтегрують зміни в спільний **trunk** (`main`) **щонайменше раз на день**
- Trunk завжди готовий до релізу
- Незавершений функціонал ховають за **feature flags**
- Ключовий елемент **CI/CD**: часті малі зміни дозволяють швидко релізити

### Як вибрати

| Тип продукту | Команда | Рекомендація |
|---|---|---|
| Будь-який, висока зрілість співпраці | мала | Trunk-based |
| Безперервний деплой (SaaS) | середня | GitHub Flow, Trunk-based |
| Релізи за розкладом (мобільні застосунки) | середня | GitFlow, GitLab Flow з release-гілками |
| Висока вимога до якості + безперервний деплой | середня | GitLab Flow |
| Висока вимога до якості + довга підтримка версій | велика | GitFlow |

## 18. Pull Request (PR)

**Pull Request** це запит на злиття ваших змін у базову гілку на GitHub. Дозволяє **обговорити й перевірити** зміни до злиття; можна додавати нові коміти вже після відкриття PR.

### Типовий робочий процес команди
1. **Власник репозиторію** запрошує колабораторів
2. Налаштовує **branch protection rules** (наприклад: тільки через PR, обов'язкове схвалення)
3. Колаборатор **клонує** репозиторій
4. Створює нову гілку
5. Вносить зміни → **commit** → **push**
6. Відкриває **Pull Request**
7. Чекає на **review**
8. Після схвалення зміни зливаються (merge)

```bash
git checkout -b feature/login
# ...код...
git add . && git commit -m "Add login form"
git push -u origin feature/login
# далі на GitHub: Compare & pull request
```

### Способи злиття PR на GitHub
- **Merge commit:** зберігає всі коміти + коміт злиття
- **Squash and merge:** всі коміти гілки в один
- **Rebase and merge:** коміти переносяться без merge-коміту

## Шпаргалка

| Задача | Команда |
|---|---|
| Клонувати | `git clone <url>` |
| Стан | `git status` |
| Додати все | `git add .` |
| Коміт | `git commit -m "msg"` |
| Відправити / отримати | `git push` / `git pull` |
| Нова гілка | `git checkout -b name` |
| Злити | `git merge name` |
| Видалити гілку | `git branch -d name` |
| Історія | `git log --oneline --graph` |
| Різниця | `git diff` / `git diff --staged` |
| Скасувати злиття | `git merge --abort` |
| Змінити останній коміт | `git commit --amend` |
| Об'єднати коміти | `git rebase -i HEAD~N` |
| Перенести гілку | `git rebase main` |
| Взяти один коміт | `git cherry-pick <sha>` |
| Скасувати коміт безпечно | `git revert <sha>` |
| Відкинути все локальне | `git reset --hard` |
| Врятувати «втрачене» | `git reflog` |
| Сховати зміни | `git stash` / `git stash pop` |
